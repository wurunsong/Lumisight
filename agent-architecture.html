Lumisight 多 Agent 主流程

上半部分只讲信息怎么流，下半部分再讲技术亮点。也就是说，先让人一眼看懂“请求怎么进来、什么时候升级、任务怎么分发、结果怎么回收”，再补计划执行、环境操作、离线反思和 RAG 评测这些工程闭环，不把两件事混成同一张说明书。

Main Flow

端到端主流程

这是用户视角下的总流程图。重点不是工具名，而是一个请求从进入系统，到决定是否升级成多 Agent，再到收敛为同一个最终回答，中间的信息如何流动。

01

请求进入

用户问题、会话上下文和控制动作一起进入统一入口，先归到同一个 session 视角里，并准备接上历史上下文。

02

会话调度

系统先决定这是继续当前执行、打断改道，还是恢复上次停住的会话，同时恢复该 session 的上下文状态。

03

模式判断

简单任务留在单 Agent；只有明显需要拆分、并行或分角色处理时，才升级到多 Agent。

04

Lead 制定计划

Lead 把请求拆成任务、依赖和执行顺序，也会吸收记忆、上下文、外挂检索与计划系统当前状态带回来的补充证据。

05

执行与回流

任务被执行后，结果、状态和证据重新汇回 Lead，并写回上下文账本，而不是散落成多个独立对话。

06

统一最终回答

所有中间结果都收敛回主会话，再由主 Agent / Lead 产出事件流和最终答案；必要时把长期事实沉淀回记忆层，并在后台形成可复用的反思结果。

上下文管理存在于主链路里

请求不是裸奔进入模型；会话历史、账本、压缩后的上下文视图会随着主流程一起参与决策和收敛。

记忆系统在旁路支持主流程

长期记忆不会替代当前会话，但会在需要时补充用户偏好、项目事实和跨会话经验，并在结束后继续沉淀有价值的信息。

外挂 RAG / 图谱是增强层

向量检索、图谱和源码增强工具不是主流程本体，但在需要额外证据时会被接入，给 Lead 或单 Agent 提供外部知识支持，并可再用公开 benchmark 反向校准检索质量。

Multi-Agent Branch

多 Agent 信息流

只有在第 3 步确定需要升级时，请求才会进入这条支线。这里强调的是 Lead 和 worker 之间的信息交换关系，以及中断后从哪里继续。

Lead / Worker 泳道图

Lead
收到复杂请求 确认进入 MULTI_AGENT 路径。
拆出任务与依赖 把一个问题变成可分发的 plan。
按 wave 派发 把 task 写给对应 worker。
汇总结果与状态 收 summary、task state、lifecycle。
收敛回主会话 继续最后的回答或下一轮动作。
Workers
等待 assignment 从 team inbox 读取自己的任务。
必要时先申请权限 不是所有动作都能直接执行。
并发执行子任务 同一 wave 内多个 worker 可以并行推进。
回传结果 把结论、状态和 idle 通知交回 Lead。
等待下一波或结束 继续协作，直到本次请求收口。

恢复点

Lead 不会等全部结束才记状态，而是每完成一波就保存当前进度。所以如果中途 interrupt，系统会在 wave 边界停住；下一次 `resume` 继续剩余任务，而不是从头再跑整套流程。

升级边界

多 Agent 不是默认行为。只有当请求天然带有“分别分析”“并行看多个模块”“前后端协同”“修复和验证分工”等信号时，系统才认为拆分比单 Agent 更值得。

最终收口

无论拆成多少 worker，最后负责写入、验证、事件输出和回答用户的仍然是主 Agent / Lead。worker 提供的是局部结果，不是最终对话主体。

执行基底

多 Agent 之下并不是“任意 shell”，而是计划系统、受控环境工具、服务日志检查和离线反思一起构成可持续推进的执行底座，Lead 只是把这些能力调度起来。

什么时候不升级

如果一个请求虽然长，但并不需要真正拆分，系统会保持单 Agent，避免把简单事做复杂。

什么时候升级

当请求需要多个局部视角、依赖收敛或者并发扫描时，Lead 才会拉起多 Agent 流程。

为什么能恢复

因为执行状态不是临时留在内存里，而是随着 wave 推进被持续保存下来。

Technical Highlights

技术亮点

上面先解决“怎么看懂流程”，下面再保留工程实现里真正有区分度的能力点。这里仍然保留技术亮点，但它们现在是补充说明，不再抢主流程的视觉重心。

默认单 Agent，谨慎升级

  • 系统不会因为具备 `task_subagent` 就默认走多 Agent。
  • 只有显式 `MULTI_AGENT` 或 auto-upgrade 信号足够强时，才进入 orchestration。
  • 这样能避免把简单请求过度工程化。

Lead 负责拆分与收口

  • Lead 负责生成 plan、管理依赖、派发任务和汇总结果。
  • 当前会按 `SERIAL_DAG`、`FAN_OUT_FAN_IN`、`HYBRID` 选择不同的编排形态。
  • worker 只是局部执行者，不持有最终回答权。
  • 主会话始终保持唯一的结果收敛点。

Worker 支持并发 wave

  • 同一波任务可以并发执行，而不是逐个串行处理。
  • 并发后仍由 Lead 统一收集 task state 和结论。
  • 这让多模块扫描和分工分析真正产生收益。

权限不是默认放开

  • worker 碰到需要额外能力的动作时，会先向 Lead 申请。
  • 批准后再继续，不批准则返回被阻断的结果。
  • 多 Agent 协作仍然服从同一套可控边界。

执行状态可持久化

  • Lead 会把执行进度持续写入状态文件。
  • 保存的不只是最终结论，还有 task state 和恢复位置。
  • 所以 interrupt 后可以从已知边界继续，而不是完全重来。

恢复仍回到同一会话

  • `resume` 不是新开一个独立多 Agent 流，而是恢复原会话的未完成部分。
  • 恢复点按 wave 和 task state 定位，不会把已经完成的子任务再跑一遍。
  • 这让用户体验保持“同一个任务持续推进”的连续感。
  • 多 Agent 最终仍然服务于主会话，而不是替代主会话。

计划系统把执行闭环固定下来

  • 主链路已经不只依赖会话内 todo，而是补齐了 `task_create / claim / release / complete / resume / board` 这一组跨会话计划语义。
  • Lead 可以围绕 ready、blocked、in-progress 和 completed 来判断下一步，而不是每轮重新猜当前推进到哪里。
  • 这样多 Agent、单 Agent 和 cron / 离线反思都能围绕同一套任务视图衔接。

环境操作仍受同一套边界约束

  • 系统现在能做依赖安装、服务启动、状态检查、日志读取和服务停止，但这些动作仍被限制在 repo 内白名单命令与托管日志路径里。
  • 触发条件是“需要把代码改动落到真实运行态或验证环境”，核心处理是受控命令执行与后台服务托管。
  • 保护措施是最小命令面、显式 serviceId、可追踪 pid / logFile，输出结果则回到主会话继续决策或修复。

离线反思把结束后的经验回流主系统

  • 请求结束不再意味着信息流断掉；后台可以读取 task board、近期 memory 和 cron 历史，生成一份离线反思摘要。
  • 这条链路的输入是执行痕迹，处理是聚合当前阻塞、失败运行和近期沉淀，保护是默认只写 `project memory` 或少量 follow-up task。
  • 输出结果不是新的聊天回答，而是让未来请求能直接复用的长期经验与下一步动作。

RAG 检索开始有公开 benchmark 校准

  • 外挂向量检索不再只是“能接进去”，而是增加了 CodeSearchNet 风格的代码检索评测入口。
  • 触发条件是需要验证 `docstring -> code retrieval` 的召回质量，核心处理是读取公开 jsonl 数据、构建临时语料库并计算 `Recall@K / MRR / mean NDCG`。
  • 这样 RAG 的价值不只停留在架构说明里，还能用公开数据集回答“检索到底召回得怎么样”。
