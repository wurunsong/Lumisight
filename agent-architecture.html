Lumisight 多 Agent 主流程

上半部分只讲信息怎么流，下半部分再讲技术亮点。现在这条链路收成了同一个执行模型：入口只接请求，应用层先完成策略判决、记忆、skill、权限和编排，只有真正进入 agent loop 时，才封装成任务信息加 loop handler 交给同一个线程池执行器。

Main Flow

端到端主流程

这是用户视角下的总流程图。重点不是类名，而是一个请求从进入系统，到决定是否升级成多 Agent，再到收敛为同一个最终回答，中间的信息如何流动，以及每一层各自只承担哪一段职责。

01

入口接住请求

用户问题、会话上下文和控制动作先进入统一入口，变成同一个 session 视角下的事件流，而不是直接散进后面的执行细节。

02

准备层确定路径

系统恢复会话态、归一化问题，并在进入执行前确定这次是单 Agent 直跑，还是需要进入多 Agent 编排。

03

统一任务分发

无论 primary 还是 sub-agent，都会先走同一个分发器完成准备；此时只确定执行画像和策略边界，不把判断逻辑塞进线程池。

04

应用层完成编排

应用协调层解析 skill、预取记忆、处理权限和恢复点；如果是多 Agent，Lead 在这里拆任务，选择 serial / parallel / hybrid 编排方式，再由调度器生成执行批次并收集子任务结果。

05

线程池执行 loop

准备和编排完成后，真正的 agent loop 才作为 task 进入线程池。单 Agent 是一个 loop task；多 Agent 是每个 wave 的多个 loop task。

06

主会话统一收敛

所有中间结果最终都回到主会话，再由主 Agent / Lead 输出事件流和最终答案；子 Agent 不绕回入口层，也不单独持有最终回答权。

上下文管理存在于主链路里

请求不是裸奔进入模型；会话历史、账本、压缩后的上下文视图会随着主流程一起参与决策和收敛。

记忆系统在旁路支持主流程

长期记忆不会替代当前会话，但会在需要时补充用户偏好、项目事实和跨会话经验，并在结束后继续沉淀有价值的信息。

外挂 RAG / 图谱是增强层

向量检索、图谱和源码增强工具不是主流程本体，但在需要额外证据时会被接入，给 Lead 或单 Agent 提供外部知识支持，并可再用公开 benchmark 反向校准检索质量。

Multi-Agent Branch

多 Agent 信息流

只有在准备层确定需要升级时，请求才会进入这条支线。这里强调的是 Lead 如何把复杂任务切成 wave，以及每个 worker 如何在编排完成后通过同一个 loop task 模型进入 agent loop。

Lead / Worker 泳道图

Lead
收到复杂请求 确认进入 MULTI_AGENT 路径。
拆出任务与依赖 把一个问题变成可分发的 plan。
按 wave 派发 把子任务整理成当前 wave 的 loop task，交给线程池。
汇总结果与状态 收 summary、task state、lifecycle。
收敛回主会话 继续最后的回答或下一轮动作。
Workers
等待 assignment 从当前 wave 的 AgentLoopTask 集合里拿到自己的任务。
继承只读边界 worker 通过同一个 loop 通道执行，但不会拿到写权限。
并发执行子任务 同一 wave 内多个 worker 可以并行推进。
回传结果 把结论、状态和生命周期结果直接返回给 Lead。
等待下一波或结束 继续协作，直到本次请求收口。

恢复点

Lead 不会等全部结束才记状态，而是每完成一波就保存当前进度。所以如果中途 interrupt，系统会在 wave 边界停住；下一次 `resume` 继续剩余任务，而不是从头再跑整套流程。

升级边界

多 Agent 不是默认行为。只有当请求天然带有“分别分析”“并行看多个模块”“前后端协同”“修复和验证分工”等信号时，系统才认为拆分比单 Agent 更值得；sub-agent 自己不会再次向下升级。

最终收口

无论拆成多少 worker，最后负责写入、验证、事件输出和回答用户的仍然是主 Agent / Lead。worker 提供的是局部结果，不会绕回外部入口，也不会绕开主会话单独收口。

权限边界

single agent 可以带写能力继续推进，但仍要经过 human gate；fan-out 期间的 sub-agent 一律只读；只有 lead 在 fan-in 完成后的收敛阶段，才重新获得有限写权限。

什么时候不升级

如果一个请求虽然长，但并不需要真正拆分，系统会保持单 Agent，避免把简单事做复杂。

什么时候升级

当请求需要多个局部视角、依赖收敛或者并发扫描时，Lead 才会拉起多 Agent 流程。

为什么能恢复

因为执行状态不是临时留在内存里，而是随着 wave 推进被持续保存下来。

Technical Highlights

技术亮点

上面先解决“怎么看懂流程”，下面再保留工程实现里真正有区分度的能力点。这里仍然保留技术亮点，但它们现在是补充说明，不再抢主流程的视觉重心。

默认单 Agent，谨慎升级

  • 系统不会因为具备 `task_subagent` 就默认走多 Agent。
  • 只有显式 `MULTI_AGENT` 或 auto-upgrade 信号足够强时，才进入 orchestration。
  • 这样能避免把简单请求过度工程化。

入口、应用层、内核已经拆开

  • 入口层只负责把请求接成事件流，不再承担整条执行主干。
  • 应用层负责 single / multi 判决、skill、权限、resume、plan 和最终答复。
  • 执行内核只打开运行作用域并驱动统一 loop，避免策略逻辑继续回流到 kernel。

统一任务分发器消除递归入口

  • `AgentExecutionTaskDispatcher` 只统一准备 primary / sub-agent，不再把整条应用层流程塞进线程池。
  • 只有 `AgentExecutionKernel.executeLoop(...)` 会被封装成 `AgentLoopTask`。
  • sub-agent 不再调用外部入口服务，也不会形成 `executePrimary -> executeChild` 的绕路。
  • 中间调度可以复杂，但最终线程池执行通道保持同构。

Lead 负责拆分与收口

  • Lead 负责生成 plan、管理依赖、派发任务和汇总结果。
  • 当前会按 `SERIAL`、`PARALLEL`、`HYBRID` 选择不同的 agent 编排方式。
  • worker 只是局部执行者，不持有最终回答权。
  • 主会话始终保持唯一的结果收敛点。

Worker 支持批次并发

  • 同一波任务会先完成准备，再把各自的 kernel loop 变成一组 `AgentLoopTask` 提交线程池。
  • 并发后仍由 Lead 统一收集 task state 和结论。
  • 这让多模块扫描和分工分析真正产生收益。

权限不再散落在流程里

  • 权限判断已经独立成统一策略，而不是继续塞在主执行流程中间。
  • single agent、lead 收敛阶段、sub-agent 各自有明确边界。
  • 这样看流程时能先看信息怎么流，再看不同角色各自能做什么。

执行状态可持久化

  • Lead 会把执行进度持续写入状态文件。
  • 保存的不只是最终结论，还有 task state 和恢复位置。
  • 所以 interrupt 后可以从已知边界继续，而不是完全重来。

恢复仍回到同一会话

  • `resume` 不是新开一个独立多 Agent 流，而是恢复原会话的未完成部分。
  • 恢复点按 wave 和 task state 定位，不会把已经完成的子任务再跑一遍。
  • 这让用户体验保持“同一个任务持续推进”的连续感。
  • 多 Agent 最终仍然服务于主会话，而不是替代主会话。

计划系统把执行闭环固定下来

  • 主链路已经不只依赖会话内 todo，而是补齐了 `task_create / claim / release / complete / resume / board` 这一组跨会话计划语义。
  • Lead 可以围绕 ready、blocked、in-progress 和 completed 来判断下一步，而不是每轮重新猜当前推进到哪里。
  • 这样多 Agent、单 Agent 和 cron / 离线反思都能围绕同一套任务视图衔接。

环境操作仍受同一套边界约束

  • 系统现在能做依赖安装、服务启动、状态检查、日志读取和服务停止，但这些动作仍被限制在 repo 内白名单命令与托管日志路径里。
  • 触发条件是“需要把代码改动落到真实运行态或验证环境”，核心处理是受控命令执行与后台服务托管。
  • 保护措施是最小命令面、显式 serviceId、可追踪 pid / logFile，输出结果则回到主会话继续决策或修复。

离线反思把结束后的经验回流主系统

  • 请求结束不再意味着信息流断掉；后台可以读取 task board、近期 memory 和 cron 历史，生成一份离线反思摘要。
  • 这条链路的输入是执行痕迹，处理是聚合当前阻塞、失败运行和近期沉淀，保护是默认只写 `project memory` 或少量 follow-up task。
  • 输出结果不是新的聊天回答，而是让未来请求能直接复用的长期经验与下一步动作。

RAG 检索开始有公开 benchmark 校准

  • 外挂向量检索不再只是“能接进去”，而是增加了 CodeSearchNet 风格的代码检索评测入口。
  • 触发条件是需要验证 `docstring -> code retrieval` 的召回质量，核心处理是读取公开 jsonl 数据、构建临时语料库并计算 `Recall@K / MRR / mean NDCG`。
  • 这样 RAG 的价值不只停留在架构说明里，还能用公开数据集回答“检索到底召回得怎么样”。
