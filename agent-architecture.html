Lumisight 多 Agent 主流程

这张图只讲一件事：用户的信息如何进入系统，什么时候保持单 Agent，什么时候升级成多 Agent，Lead 如何拆任务，worker 如何回传，最后又怎样收敛回同一个最终回答。

端到端主流程

这是用户视角下的主信息流。重点不是工具细节，而是请求从进入到产出结果，中间经过了哪些关键决策点。

1. 请求进入 用户问题、session、控制指令进入统一会话入口。
→
2. 会话调度 系统决定这是继续当前会话、打断重定向，还是恢复上次执行。
→
3. 模式判断 简单任务留在单 Agent，复杂任务才升级到多 Agent。
→
4. 计划生成 Lead 把问题拆成一个或多个可执行任务，并决定拓扑。
→
5. 执行与汇总 单 Agent 直接执行，多 Agent 则分发给 worker，再回到 Lead 汇总。
→
6. 最终回答 所有结果重新回到主会话，统一输出事件流和最终答案。

多 Agent 信息流

只有在第 3 步判断需要升级时，主流程才会进入这条分支。这里的重点是 Lead 和 worker 之间的信息怎样来回流动，以及恢复点在哪里。

Lead 与 Worker 的流向

Lead
收到复杂请求 进入 MULTI_AGENT
→
拆成任务 生成 plan 与依赖
→
按 wave 派发 把 task 发给 worker
→
汇总结果 收 task state 和结论
→
收敛回主会话 继续最终回答
Workers
等待任务 读取 assignment
→
必要时申请权限 先问 Lead 再继续
→
执行子任务 并发分析或修复
→
回传结果 summary、state、idle
→
等待下一波 或结束本次协作

恢复点在哪里

  • Lead 每完成一波任务，都会保存当前执行状态。
  • 如果用户中断，会在 wave 边界停下来，而不是把半波状态写乱。
  • 下一次 `resume` 不会从头再来，而是只继续剩下的 pending 任务。
  • 所以多 Agent 最终仍然服务于同一个主会话，而不是散成几个独立对话。

什么时候不升级

如果一个请求本身很直接，或者虽然复杂但不值得拆分，系统就继续走单 Agent，避免为了多 Agent 而多 Agent。

什么时候升级

当问题天然需要“分别分析”“并行看多个模块”“前后端协同”“修复加验证分工”时，Lead 才会拆计划并拉起 worker。

最后谁负责收口

无论中间拆成多少任务，最终写入、验证、事件输出和回答用户的始终是主 Agent / Lead，而不是某个 worker。
