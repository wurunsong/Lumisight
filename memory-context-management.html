Main Flow

端到端主流程

这是“上下文和记忆如何服务一次请求”的总流程。重点不是配置名，而是用户输入、历史上下文、相关记忆和外挂证据如何一步步变成真正给模型看的 prompt 视图。

01

请求进入会话

用户输入先回到当前 session，而不是直接裸奔给模型；这一步决定后续要恢复哪份上下文状态。

02

恢复上下文账本

系统恢复会话账本、历史 entry、artifact 引用和当前轮次状态，建立这一轮的工作上下文基线。

03

补充相关记忆

长期记忆系统按当前问题同时查看用户域和项目域，挑选相关事实、偏好和项目经验，作为旁路证据补进这轮推理准备阶段。

04

投影与压缩

不是把完整历史都喂给模型，而是先做 artifact 落盘、Snip、Micro-Compact、Projection，生成一份更值钱的上下文视图。

05

模型推理与回写

模型基于投影视图完成决策；工具结果、验证信息和新结论再回写到账本，而不是只停留在瞬时响应里。

06

维护与结束

这一轮结束后，会话上下文继续保留在账本层；真正值得长期保存的事实会进入记忆维护决策，再按作用域写到用户 home 或当前仓库。

上下文是主链路

会话账本、artifact 和投影不是可选项，而是每一轮模型调用前都会经过的核心路径。

长期记忆是旁路支持

长期记忆不会替代当前会话，但会在准备阶段补充跨会话事实，并在结束后用维护决策修正长期记忆；用户身份和偏好不再误写到项目仓库。

外挂检索是增强层

RAG、图谱和源码增强工具不是记忆系统本体，但会在需要更多证据时被接到同一套上下文准备链路里；检索质量也可以再用公开 benchmark 做校准。

Two Layers

会话上下文与长期记忆

这两层都服务于同一次请求，但职责不同：会话上下文负责“这一轮现在要看什么”，长期记忆负责“跨会话该记住什么”。

为什么要分两层

因为“这轮会话里发生了什么”和“以后都该记住什么”不是同一类信息。前者要完整、可追溯，后者要更稳定、更克制，否则会把噪音固化成长久事实。

为什么还要分作用域

因为“用户是谁、偏好是什么”和“这个仓库里的事实是什么”生命周期不同。用户记忆应该跟着人走，项目记忆应该跟着仓库走；混在一起会让换仓库后的回答变脏。

压缩不是为了删历史

压缩的目标不是抹掉发生过的内容，而是把大结果、老内容和可重取证据转成更轻的视图，让模型上下文预算花在当前最有价值的信息上。

外挂检索插在哪里

RAG、图谱和方法源码增强不直接替代记忆，也不替代会话账本。它们更像证据放大器，在准备阶段提供外部补充，再通过同一套上下文链路进入模型视图；现在还可以用公开代码检索 benchmark 校准这层增强质量。

什么时候落盘

当单条结果或单轮工具输出过大时，完整正文先写 artifact，prompt 里只保留 preview 和引用。

什么时候压缩

当 token 预算逼近窗口边界时，系统优先折叠旧对话和可重取工具结果，而不是马上全量摘要。

什么时候维护记忆

不是每条内容都进长期记忆。系统只在出现用户偏好、项目事实、稳定经验或旧记忆需要修正时，才触发新增、更新、合并或删除，并按类型选择用户域或项目域。

什么时候做离线反思

当任务看板、近期记忆和 cron 历史里已经积累出阶段性模式时，系统可以在主执行链外再整理一次，产出更稳定的 project memory。

Technical Highlights

技术亮点

上面先让人看懂记忆系统和上下文系统如何存在于主流程里，下面再保留工程层真正关键的实现亮点。

会话账本不是字符串列表

  • 系统保存的是结构化上下文 entry，而不是一串不断膨胀的消息文本。
  • 这样后续投影、压缩、artifact 引用和恢复都有统一抓手。
  • 上下文决策从“堆历史”升级成了“管理账本”。

Artifact 让大结果可追溯

  • 大结果先落盘，再在 prompt 里保留轻视图。
  • 模型不需要吞完整正文，但系统也不会失去完整证据。
  • 这解决了“完整保留”和“上下文预算”之间的冲突。

Projection 先于模型调用

  • 模型看到的是读时投影后的视图，而不是原样账本。
  • 不同阶段可以共享同一账本，但拿到不同视图。
  • Artifact、Snip、Micro-Compact 和 Auto-Compact 会在投影前后协同工作。
  • 这让预算管理发生在模型调用前，而不是调用失败后。

记忆检索是预取型旁路

  • 相关记忆会在请求准备阶段提前挑选，而不是等模型临时想起再补。
  • 这让长期经验更自然地进入一次推理，而不打乱主会话结构。
  • 长期记忆因此更像稳定支撑层，而不是另一本对话日志。

会话层和记忆层职责分离

  • 会话层追求完整可恢复，记忆层追求长期有效和克制写入。
  • 两层都服务当前请求，但保留粒度和生命周期不同。
  • 这避免了把短期噪音直接变成永久知识。

记忆落盘按作用域分域

  • `user` 和 `feedback` 记忆写入用户 home 下的 Lumisight 记忆空间，服务跨仓库连续性。
  • `project` 和 `reference` 记忆仍保留在当前仓库 `.lumisight/memory`，服务项目事实追踪。
  • `memory_list` 会同时合并用户域和项目域，所以读取体验保持统一，写入边界保持清楚。

Hot Cache 让恢复更像连续工作

  • Auto-Compact 后系统会优先记住最近访问的文件、工具证据和活跃工作面。
  • 下一轮恢复时不必把所有老内容重新展开，而是先把最热的上下文片段捞回来。
  • 这让压缩后的会话仍然保留“工作连续性”，而不是只剩一段冷摘要。

外挂 RAG / 图谱并入同一准备链路

  • 向量检索、图谱和源码增强会在需要时为主流程补证据。
  • 这些证据仍通过同一套上下文准备机制进入 prompt。
  • 现在这层检索质量还可以用 CodeSearchNet 风格 benchmark 进一步校准。
  • 所以外挂能力是增强层，而不是与记忆系统割裂的另一条暗线。

自动记忆维护不是只追加

  • 最终回答后会异步投递记忆信号，不阻塞用户侧响应。
  • 维护模型会同时看到裁剪后的本轮上下文、MEMORY.md 索引和相关旧记忆。
  • 输出不再只是 shouldWrite，而是 CREATE / UPDATE / MERGE / DELETE / NONE。

离线反思复用同一份账本与记忆信号

  • 离线反思不会绕开主系统，而是回看 task board、近期记忆和 cron 历史这些已有信号。
  • 输出仍会回到 project memory，必要时再转成少量 follow-up tasks。
  • 这让“执行后的整理”也复用同一套上下文和记忆资产，而不是另起一套孤立流程。
