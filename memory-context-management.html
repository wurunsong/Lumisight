Lumisight 记忆地形图

这页把记忆系统画成一张会流动、会沉积、也会主动退潮的地图。上半部分先讲一次请求里，上下文账本如何被恢复、压缩、投影给模型；长期记忆如何在 user / feedback / project / reference 四个域里被挑选、维护，以及为什么只有工程记忆会在过旧时进入遗忘衰减与自动归档。

Main Flow

一次请求里的记忆主潮汐

先看主潮汐，而不是配置表。这里讲的是：一个请求进入系统以后，短期上下文如何先被恢复和瘦身，长期记忆如何只在需要时补进来，最后又怎样把新事实谨慎地回收到可持续复用的层里。

01

请求回到当前会话

用户输入不会直接裸奔给模型，而是先回到 `sessionId` 对应的会话账本。这样系统才能知道这轮应该接着哪段工作面继续。

session first
02

恢复账本与热区

系统恢复历史 entry、artifact 引用、hot cache 和本轮状态，重新拼出当前最可能有用的上下文地形，而不是机械回放整段对话。

restore + hot cache
03

预取相关长期记忆

Relevant memory service 会从用户域和仓库域挑选与当前问题最相关的长期事实，把它们作为旁路证据补入准备阶段。

prefetch lane
04

投影、落盘与压缩

大结果先 artifact 化，老内容按预算进入 snip、micro-compact 和 projection。模型拿到的是高价值视图，不是全量历史副本。

projection first
05

推理后回写账本

工具结果、验证证据和新结论会继续回写到账本里，让下一轮恢复时仍保留连续工作感，而不是只剩最终回答。

write back
06

维护、遗忘与结束

真正值得跨会话保存的事实才会进入长期记忆维护；只有过老的 `project / reference` 记忆才会先衰减权重，再进入 `.forgotten` 归档，不让工程记忆库无限膨胀。

decay + archive

上下文是主链路

会话账本、artifact、projection 和压缩是每轮调用前都要经过的主链路，不是聊天框旁边的附加功能。

长期记忆是旁路支持

长期记忆不会替代当前会话，但会在准备阶段补入跨会话稳定事实；写回时也不是无脑追加，而是经过维护决策和类型分域。

遗忘现在是显式机制

记忆不再只是“陈旧提醒”。现在只有旧的工程记忆会先衰减召回权重，超过硬阈值后把 `project / reference` 自动移入 `.forgotten`，把空间留给真正还在流动的项目知识。

Two Layers

会话层与长期层如何分工

这两层都服务同一个请求，但职责完全不同。会话层负责“这一轮现在要看什么”，长期层负责“跨会话仍值得留下什么”；遗忘机制则负责“哪些事实应该慢慢退出主记忆海面”。

双层信息流

Session Context
接收新输入 用户消息、工具结果和验证证据先进入结构化账本，而不是直接拼成一长段聊天历史。
预算触发瘦身 大块内容优先落到 `.lumisight/context-artifacts`，旧 entry 根据 token 预算走 snip 和 micro-compact。
读时生成投影 模型看到的是本轮读时投影后的视图，不是账本原文。真正昂贵的内容只在需要时恢复。
推理后继续回写 新结论不会悬空留在最终回答里，而是回到账本中，给下一轮恢复、验证和离线反思继续复用。
Long-Term Memory
按问题挑选 Relevant memory service 会同时看用户域和项目域，只把当前问题真正可能用到的长期事实补进本轮准备阶段。
按类型落盘 `user / feedback` 跟着人走，落到 `~/.lumisight`；`project / reference` 跟着仓库走，落到 `.lumisight/memory`。
异步维护决策 最终回答后，维护模型会判断 CREATE / UPDATE / MERGE / DELETE / NONE，而不是把所有东西都 append 成新记忆文件。
进入遗忘通道 旧的 `project / reference` 先降召回权重，再在超过 hard window 后进入 `.forgotten`，让长期层保持活性而不是越堆越脏。

为什么必须分两层

因为“这轮发生了什么”和“以后都该记住什么”本来就不是同一种资产。前者需要完整可回放，后者需要克制、稳定、可跨会话复用。

为什么还要分域

用户身份和偏好应该跟着人走，项目事实和参考资料应该跟着仓库走。把两者混成一个目录，会让换项目后的回答带上旧仓库的脏上下文。

压缩不是删除历史

压缩只是把高体积、低即时价值的内容变成更轻的工作视图；完整证据仍通过 artifact 和 hot cache 保留下来，必要时还能恢复。

遗忘也不是粗暴删库

这版遗忘先做软衰减，再做硬归档，并且只默认处理 `project / reference`。用户偏好和明确反馈不会因为久一点没用就被自动清掉。

Forgetting Flow

记忆如何退潮，而不是永远堆高

这部分专门讲新加的遗忘机制。重点不是“系统终于会删文件”，而是它现在开始把工程记忆当成一个有生命周期的层：先提醒、再降权、最后归档，给新项目知识腾出主航道；用户画像和明确反馈不走这条衰减通道。

遗忘时间线

Fresh Zone 新记忆保持全权重

刚写入或最近仍被更新的长期记忆，会以完整权重参与启发式召回，也会继续出现在 `MEMORY.md` 的主索引里。

Stale Reminder 先出现陈旧提醒

超过 `stale-after-days` 后，系统先把它标成“某个时间点的观察”。这一步不删除记忆，但会提醒使用方先对照当前代码或事实验证。

Soft Forgetting 进入召回衰减期

超过 `soft-forget-after-days` 后，旧记忆不再因为 `mtime` 老而自然吃分，反而会逐步降低检索权重。长期经验还能被用，但不再轻易压过更新鲜的事实。

Hard Archive 超期归档到 `.forgotten`

超过 `hard-forget-after-days` 且类型属于 `project / reference` 时，文件会从主记忆目录移到 `.forgotten`。它不是彻底销毁，而是退出主航道。

默认只归档哪些类型

当前默认只对 `project` 和 `reference` 做自动归档和软衰减，因为它们更容易随着项目推进变旧。`user` 和 `feedback` 更偏长期人格与约束，不应轻易被时间因素削弱。

为什么选归档而不是直接删

归档保留了恢复可能性，也让系统能把“退出主记忆面”与“永久删除”分开。这样记忆库会更干净，但不会因为一次激进清理就丢掉潜在有用的历史背景。

这条链路接在哪

自动归档发生在记忆扫描与加载入口附近，也就是说每次系统重新看主记忆目录时，都会顺手把已超期的旧项目记忆退到归档层。

什么时候 artifact 化

当单条结果或单轮工具输出过大时，完整正文先写 artifact，prompt 里只保留 preview 和引用，把上下文预算留给当前轮真正要判断的东西。

什么时候压缩

当投影预算逼近窗口边界，系统优先折叠旧对话和可恢复证据，而不是等模型已经超窗后再补救。

什么时候写长期记忆

只有出现稳定偏好、持续项目事实、明确反馈或长期参考时，系统才会写入长期层；普通工具流水和一次性状态不会直接固化。

什么时候触发遗忘

当工程记忆足够久未更新时，系统先用陈旧度提醒和召回衰减降低影响；超过 hard window 后，再把 `project / reference` 移入 `.forgotten`。

Technical Highlights

工程亮点

上面先把记忆系统讲成一张信息流地图，下面再保留真正有工程密度的差异点。它们是补充层，不抢主潮汐的视觉位置。

会话账本不是字符串堆

  • 上下文保存的是结构化 entry、artifact 引用和热区信息，而不是一段不断膨胀的聊天文本。
  • 这让恢复、投影、压缩和回写都有统一抓手。

Projection 发生在模型前

  • 系统先决定“模型这轮真正该看到什么”，再去调用模型。
  • 预算管理因此发生在调用前，而不是超窗后才亡羊补牢。

Artifact 保留完整证据

  • 大结果先落到 `.lumisight/context-artifacts`，prompt 里只保留 preview、summary 和定位信息。
  • 这同时解决了“完整保留”和“上下文预算有限”的冲突。

长期记忆是预取型旁路

  • 相关记忆会在请求准备阶段预先挑选，而不是等模型生成到一半才临时追问“有没有旧经验”。
  • 长期层因此更像稳定支撑面，而不是第二本对话日志。

自动维护不再只有追加

  • 记忆维护模型会综合当前上下文、`MEMORY.md` 索引和已选旧记忆，输出 CREATE / UPDATE / MERGE / DELETE / NONE。
  • 系统开始把长期层当成需要整理的知识库，而不是 append-only 文本堆。

遗忘机制开始进入主设计

  • 旧的工程记忆先做陈旧提醒，再做召回衰减，最后把超期 `project / reference` 归档到 `.forgotten`。
  • 这让记忆系统第一次具备“退出主记忆面”的显式机制，而不只是永远保留所有历史文件。
