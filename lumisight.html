Lumisight 完整架构总览

这页先讲 Lumisight 作为一个本地 Agent 系统，用户请求如何进入、如何被调度、在哪里接上上下文和记忆、什么时候升级成多 Agent、又如何带着验证与长期记忆维护收口。多 Agent 细节不在这里展开到最深，那部分继续由专项页负责。

Session-First Runtime Context And Memory Aware Safe Tool Execution Escalate On Demand
Main Flow

端到端主流程

重点不是模块名，而是一个请求从进入系统，到被理解、执行、验证，再到把结果沉淀回会话、任务和记忆层，中间的信息如何闭环。

01

会话命令进入

用户通过 SSE、WebSocket、调试页或桌面壳把问题、恢复、打断等命令送进同一个 `sessionId` 视角，系统先统一看成“同一会话上的下一次动作”。

02

调度与交互模式判断

dispatcher 先决定是 `FOLLOW` 顺序推进、`COLLECT` 合并等待输入，还是 `STEER` 抢占当前执行；必要时恢复等待态、todo 和中断后的执行位置。

03

上下文与记忆接入

模型不是裸奔开工。会话账本、artifact、hot cache、长期记忆和必要的外挂证据会先被投影成当前轮真正需要的上下文视图。

04

规划执行路径

系统先判断这是单 Agent 直接处理、调用 `task_subagent` 做干净局部分析，还是升级到 Lead + workers 的多 Agent 编排；同时把约束、skill 和计划带入本轮决策。

05

执行、验证与回流

工具执行可触达代码、Git、浏览器、图谱、向量、任务与记忆接口，但都要经过受限执行边界；写 Java 后还会自动编译 / lint，把失败结果继续回灌上下文。

06

事件输出与长期维护

结果以会话事件流和最终回答回到用户侧，同时把有价值的信息写回上下文账本、持久化任务、execution state；长期记忆则由异步维护决策判断是否新增、更新、合并或删除。

多 Agent 是升级支线

复杂请求才升级，不把所有任务都拆成 team；默认仍优先保持单 Agent 路径。

浏览器与 RAG 是证据层

Playwright、源码、图谱和向量检索不替代主流程，只在需要额外证据时进入回路。

任务系统负责跨会话推进

`todo_write` 解决当前会话内计划，`.tasks/` 里的持久化任务图负责跨会话阻塞、认领与解锁。

记忆层维护长期事实

长期记忆只保留用户、反馈、项目和参考这四类稳定信息；结束后不是盲目追加，而是先判断是否应该新增、修正、合并或删除。

Capability Layers

能力协同面

下面这层不再按“请求时间线”看，而是把 Lumisight 的核心运行面拆成三条长期存在的协同层：会话控制层、执行增强层、沉淀恢复层。

三层协同泳道

会话控制层
统一会话入口 SSE、WebSocket、桌面壳和调试页都进入同一 `sessionId` 调度语义。
FOLLOW / COLLECT / STEER 系统在消息投递层决定排队、合并还是抢占，不把交互语义留给前端猜。
单 Agent 或升级 默认直走单 Agent，必要时切到 subagent 或多 Agent 编排，但主会话保持唯一收敛点。
真实事件流回给用户 `PLAN / TOOL / TOKEN / FINAL` 持续输出，不必等整轮结束才知道系统在做什么。
执行增强层
本地代码与 Git 工具 文件、编译、Lint、LSP、Git 语义工具组成默认执行面。
浏览器与页面验证 浏览器工具让本地页面打开、识别 DOM、点击输入和截图验证进入同一闭环。
图谱与向量增强 当问题需要额外证据时，再调用源码、图谱和向量检索补强决策依据。
写后自动自验证 BUG_FIX 模式在写 Java 后自动编译和 JDTLS Lint，失败就继续修，而不是提前宣布完成。
沉淀恢复层
结构化上下文账本 会话历史不再只是字符串堆叠，而是 entry、artifact、投影和压缩链路。
长期记忆维护与陈旧度提醒 记忆只保留跨会话仍值得复用的事实，取回时提醒陈旧风险，结束后通过维护决策避免重复和冲突。
任务与执行状态持久化 `.tasks/`、team execution state 和等待态恢复点，让跨会话推进、resume 和依赖解锁变得可追踪。
定时触发入口 cron job 可以按计划重新拉起同一套 Agent 主链路，让固定巡检不必每次人工发起。

什么时候升级多 Agent

当一个请求天然需要并发扫描、多视角分析、依赖收敛，或者“实现与验证分工”时，系统才值得把它升级成 Lead + workers 的编排路径。

什么时候只用 subagent

如果只是某个局部分析会污染主上下文，但还不值得拉起完整 team，主 Agent 会更倾向于调用 `task_subagent` 做干净隔离。

为什么这页不细拆多 Agent

这页的主角是整个系统。Lead、worker、wave 恢复、权限申请和 mailbox 协议已经在 `agent-architecture.html` 作为多 Agent 专项页单独展开。

Technical Highlights

技术亮点

这些亮点解释 Lumisight 为什么不像一个只会顺序调用工具的简单流水线，但它们仍然是补充层，不喧宾夺主。

会话先于请求

系统把“继续、恢复、打断、追问”都纳入同一会话模型，而不是让每个 HTTP 请求都自成一次孤立执行。

上下文是结构化资产

上下文通过 artifact、hot cache、投影和压缩来控体积、保可恢复性，避免长会话越跑越重。

长期记忆不冒充权威

记忆被限制在四类长期事实里，并带陈旧度提醒；自动维护会优先更新或合并已有事实，降低历史经验重复、冲突或过期的风险。

执行边界默认受限

工具、Hook、浏览器和写文件能力都被放在统一受限执行边界里，并与快照、回滚和人工门控组合使用。

改代码后必须自证

BUG_FIX 模式要求系统拿编译和 lint 结果为修改负责，减少“改了但没证据”这种表面完成。

升级是为了降噪，不是炫技

多 Agent、subagent、RAG 和浏览器工具都只在它们能明显降低主会话噪音、补证据或提升推进效率时才启用。
